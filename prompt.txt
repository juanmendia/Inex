==================================================
1. CONCEPTO GENERAL DEL PRODUCTO
==================================================

La aplicación será una plataforma de Recursos Humanos para múltiples empresas.

Cada empresa tendrá su propio espacio aislado dentro de la plataforma.

Ejemplo:

PLATAFORMA
│
├── Empresa A
│   ├── Administradores RRHH
│   ├── Empleados
│   └── Información propia
│
├── Empresa B
│   ├── Administradores RRHH
│   ├── Empleados
│   └── Información propia
│
└── Empresa C
    ├── Administradores RRHH
    ├── Empleados
    └── Información propia

NUNCA un usuario de una empresa debe poder acceder a información de otra empresa.

La arquitectura debe ser realmente multi-tenant.

La empresa debe poder:

- Crear empleados
- Editar empleados
- Desactivar empleados
- Cargar recibos
- Asignar recibos a empleados
- Consultar el estado de los recibos
- Ver quién firmó
- Ver quién no firmó
- Ver quién firmó en disconformidad
- Responder consultas de empleados
- Gestionar eventos
- Gestionar comunicaciones
- Administrar usuarios y permisos

El empleado debe poder:

- Iniciar sesión
- Ver su dashboard
- Ver sus recibos
- Descargar sus recibos
- Firmarlos en conformidad
- Firmarlos en disconformidad
- Indicar el motivo de la disconformidad
- Ver recibos pendientes
- Ver recibos firmados
- Ver recibos firmados en disconformidad
- Consultar a Recursos Humanos
- Ver cumpleaños
- Ver eventos
- Ver comunicaciones
- Gestionar su perfil

==================================================
2. OBJETIVO DEL PRODUCTO
==================================================

El sistema debe parecer un producto SaaS profesional, moderno y corporativo.

No quiero un sistema administrativo antiguo.

La experiencia debe ser similar a una plataforma moderna de gestión empresarial.

Debe funcionar perfectamente:

- Desktop
- Notebook
- Tablet
- Mobile

El idioma inicial será español.

El sistema debe estar preparado para internacionalización futura.

Aunque intente manipular la URL o realizar una llamada manual a la API.

Hay una cosa que cambiaría del roadmap

Aunque el motor de liquidación puede quedar para una segunda etapa, yo le diría a Cursor que lo tenga en cuenta desde el modelo de datos inicial.

Porque mirá la potencia que puede terminar teniendo:

Empleado

→ pertenece a un CCT
→ tiene categoría
→ tiene jornada
→ tiene horario
→ ficha entrada/salida
→ genera asistencia
→ genera horas extras
→ RRHH las aprueba
→ pasan como novedades
→ el motor liquida
→ genera el recibo
→ el empleado recibe el PDF
→ firma
→ queda auditado.

Eso ya no es solamente un portal de empleados. Es prácticamente un ERP de RRHH especializado.

Y el fichaje móvil lo haría así
